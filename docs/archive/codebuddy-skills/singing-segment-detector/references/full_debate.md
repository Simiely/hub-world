# 三方技术辩论：混合视频中「唱歌片段」时间戳提取方案

> 目标：在一段长视频里，同时含有 **多段谈话（speech）**、**多段背景音+文字（BGM + on-screen text）**、**多段唱歌（singing）**，自动找出**所有唱歌片段的起止时间戳**。
>
> 评判标准：**稳定好用**（可重复、能兜底、少人工） + **性能好**（准确率高、跑得快、资源省）。
>
> 形式：A 先提案 → B 批评+新方案 → C 批评+新方案 → 循环，直到三人收敛。

---

## 0. 难点拆解（三人共识前提）

| 干扰类型 | 与「唱歌」的混淆点 | 关键区分信号 |
|---|---|---|
| 谈话 / 旁白 | 同样是人声 + 可能带轻音乐 | 无旋律线、无持续音、音高抖动大 |
| 背景音 + 文字 | 有音乐 + 可能有人声旁白（voiceover） | 人声为说话而非歌唱；画面有持续文字overlay |
| 唱歌 | 人声 + 伴奏 | 清晰稳定的基频、旋律起伏、颤音、与节拍对齐 |

**最核心的技术难题**：在「人声 + 伴奏」混合信号里，**把「唱」和「说」分开**（尤其 voiceover 念稿配 BGM 时，两者都带音乐，极易误判）。纯能量/VAD 必然翻车。

---

## 1. 三人人设

| 角色 | 外号 | 信仰 | 默认武器 |
|---|---|---|---|
| **A** | 稳哥 | 「能稳定跑起来的简单方案才是好方案」 | ffmpeg + librosa 纯信号处理、零重依赖 |
| **B** | 模型姐 | 「数据驱动优于拍脑袋阈值」 | Demucs 人声分离 + 预训练歌声检测模型 |
| **C** | 老周 | 「稳定、可部署、必须有兜底」 | 混合架构 + 性能优化 + 多模态兜底 |

---

## 2. 第一轮

### 2.1 A 提案：纯信号处理启发式

> 「别上模型，太重。我的方案就三步：
> 1. `ffmpeg` 抽音频成 16k mono wav；
> 2. WebRTC VAD 切出所有『有声段』；
> 3. 对每个有声段用 `librosa.pyin` 算音高曲线，再量几个指标：音高**连续性**（voiced 占比）、**稳定性**（窗口内基频方差）、**旋律移动量**（相邻帧基频差）、**颤音**（5–7Hz 调制）。满足『持续有稳定音高 + 有旋律起伏』就判为唱歌。
>
> 优点：librosa 一个库搞定，CPU 秒级，任何环境都能跑，零模型依赖。判定规则透明，好调试。」

### 2.2 B 批评 A + 提新方案

**B 的批评（A 方案的硬伤）：**
- **在混合信号上直接做音高跟踪是噪声灾难**。唱歌片段几乎都带伴奏，pyin 在鼓点/贝斯/和声上会频繁误跟踪，voiced 占比和方差指标被伴奏污染，阈值极其脆弱。
- **说话也可能『有旋律』**：情绪化朗读、广告配音、rap、带唱腔的旁白，都会触发"有旋律起伏"，**误报率（FP）会很高**。
- **voiceover 配 BGM** 这个场景，A 的方案和唱歌几乎无法区分——因为两者都是"人声+音乐"，A 没有把人声先抽出来。
- 阈值（方差、移动量）是**针对特定录音调的**，换一档设备/换一个视频就漂移，违背"稳定好用"。

**B 的新方案：人声分离 + 预训练歌声检测**
> 1. `ffmpeg` 抽音频；
> 2. **Demucs（htdemucs）** 把音轨拆成 `vocals` / `drums` / `bass` / `other`，只取 **vocals 干声**；
> 3. 在 vocals 干声上跑一个**预训练歌声检测模型**（mel-spectrogram CNN，参考 MIREX Singing Voice Detection 任务、VocalSet 训练集），做**帧级 singing / speech 分类**；
> 4. 后处理：中值滤波去毛刺 + 最短时长过滤（唱歌段通常 ≥3s）+ 间隙合并（gap<1s 合并）。
>
> 优点：人声先被抽干净，分类交给数据驱动的小模型，跨视频泛化远强于手写阈值；帧级输出天然就是时间戳。

### 2.3 C 批评 B + 提新方案

**C 的批评（B 方案的工程风险）：**
- **Demucs 太重**：htdemucs 全模型 CPU 上分离一首 4 分钟歌要 1–2 分钟，长视频（几十分钟）直接不可接受；而且**默认把『说话声』也并进 vocals**，所以第 3 步那个模型依然要自己区分"唱 vs 说"，B 没说清这点——voiceover 误判风险并没消除。
- **单模型无兜底**：模型在罕见音色/儿歌/戏腔上可能整段漏检，一旦翻车没有退路，违背"必须有兜底"。
- **纯音频对『背景音+文字』无能为力**：当画面是"持续字幕 + BGM、人声只是念稿"时，仅靠音频很容易把念稿当唱歌。

**C 的新方案：混合 + 多模态兜底 + 性能档位**
> 1. 抽音频（ffmpeg，缓存复用）。
> 2. **人声分离可插拔**：默认用 **Spleeter 2stem（vocals/acc）** 做轻量分离（CPU 快很多），追求精度时切 Demucs。
> 3. **双信号判唱**，不押宝单一模型：
>    - 信号层：`CREPE` 或 `pyin` 在 vocals 干声上取音高，算"持续音高占比 + 颤音指数"作**硬规则**；
>    - 模型层：轻量 CNN（YAMNet 微调 / 小型 SVD 模型）输出帧级 singing 概率；
>    - **融合**：规则 AND/OR 模型概率，互相校验。
> 4. **多模态兜底**：对音频置信度处于灰区的片段，用 **OCR（画面文字密度）** 判定——若画面长时间铺字幕且无人嘴型特写，倾向判为「BGM+文字」而非唱歌，压掉 FP。
> 5. **性能档位**：`fast`（仅启发式，秒级） / `accurate`（分离+模型） / `verify`（灰区再上多模态）。
> 6. 稳定性：ffmpeg 失败回退、进度日志、阈值全配置化、结果缓存。

## 3. 第二轮

### 3.1 A 批评 C + 改进

**A 的批评：**
- C 把 Spleeter/Demucs/CREPE/ CNN/OCR 全堆上来，**部署复杂度爆炸**，和"稳定好用"背道而驰——用户装一圈依赖就劝退了。
- OCR 多模态要逐帧抽帧 + 跑识别，**性能账没算清**，长视频成本可能比音频还高。

**A 的改进（回归简化，但吸收 C 的"分离"思想）：**
> 砍掉多模态和重模型。**只保留一条主线**：
> 1. Spleeter 2stem 抽 vocals（轻）；
> 2. 在 vocals 上用 **WebRTC VAD 找有声段** + **pyin 音高**；
> 3. 判唱规则改为更鲁棒的**两条同时成立**：(a) voiced 占比高且连续；(b) 存在**规律颤音**（FFT 检测 5–7Hz 调制）——说话几乎没有规律颤音，这是唱/说最强区分项；
> 4. 最短 2.5s 过滤 + 合并。
>
> 保留 C 的"档位"和"配置化"，但**不碰 OCR、不碰大模型**，把依赖压到 ffmpeg + Spleeter + librosa 三件套。

### 3.2 B 批评 A + 改进

**B 的批评：**
- A 新方案靠"颤音"做硬规则，**儿歌、说唱、气声唱法、某些戏腔根本没有明显颤音**，会大面积漏检（FN 高）；而情绪化朗读偶尔也有微颤，**FP 仍有**。
- 纯规则在"念稿配 BGM"上仍无解法——这是用户明确提到的三类之一，**不能假装看不见**。

**B 的改进（回模型，但轻量化）：**
> 接受 A 的"三件套依赖"约束，但把第 3 步换成**一个很小的帧级分类模型**（不在全曲上跑 Demucs，只在 vocals 干声上跑一个 ~几 MB 的 CNN，ONNX Runtime CPU 推理，毫秒级/帧）：
> 1. Spleeter 抽 vocals；
> 2. vocals → mel-spectrogram → **小型 SVD-CNN（ONNX）** 输出帧级 singing 概率；
> 3. **保留 A 的颤音/音高规则作为"高置信快捷通道"**：规则命中直接判唱，跳过模型，省算力；规则灰区才调模型；
> 4. 后处理同前。
>
> 这样既保住"轻依赖 + 快"，又用模型补上规则的漏检，且模型只在灰区触发，**性能可控**。

### 3.3 C 批评 B + 改进

**C 的批评：**
- B 终于承认要多模态才能解决"念稿配 BGM"，但又把它整段砍了，只靠音频模型——**灰区里的 voiceover 仍会漏到唱歌里**。
- 模型"只在灰区触发"听起来省，但**灰区定义本身要靠规则算**，规则不稳则灰区划分也不稳，连锁脆弱。
- 没给**可量化的验收口径**：什么叫"稳定好用、性能好"？没有指标等于没法交付。

**C 的改进（收敛骨架，补齐验收与兜底）：**
> 把三人贡献拧成一条**可配置、有兜底、可度量**的主线：
> 1. 抽音频 + **Spleeter 2stem 抽 vocals**（默认轻量；`accurate` 档换 Demucs）；
> 2. **双层判唱，互补不互斥**：
>    - 规则层（快、零模型）：VAD + 音高持续度 + 颤音指数 → 高置信直接判；
>    - 模型层（小 CNN/ONNX）：对规则未决片段做帧级分类；
> 3. **多模态只在"真灰区"兜底**：仅当音频置信度落在 [0.3,0.7] 且片段时长>5s 时，才抽关键帧做 OCR 文字密度判定，压掉"念稿+BGM"类 FP——**绝大多数片段不触发，性能账可控**；
> 4. 后处理：中值滤波 + 最短 2.5s + 间隙 1s 合并 + 置信度输出；
> 5. **验收口径**（共识交付标准）：在自有 10 段混合样本上，唱歌段 **召回 ≥95%、精确 ≥92%**；单小时视频 `fast` 档 <3 分钟、`accurate` 档 <15 分钟（CPU）；任意一步失败有回退且不全盘崩。

---

## 4. 第三轮：收敛与共识

三人不再互相推翻，对以下要点达成一致：

1. **必须先抽人声再判唱**（A 吸收 B/C：混合信号直接判唱必崩）。
2. **规则 + 小模型互补**，规则做高置信快通道、模型补漏检（B 吸收 A：不堆重模型；A 吸收 B：不纯靠脆阈值）。
3. **多模态仅作灰区兜底**，不全程启用（C 吸收 A/B：性能可控；A/B 吸收 C：念稿+BGM 必须有解法）。
4. **档位化 + 配置化 + 兜底回退**，把"稳定好用"落到工程（C 主线）。
5. **用可量化指标收口**，否则无法判定达标（C 补的验收）。

---

## 5. 最终共识方案（交付规格）

### 5.1 处理流水线

```
视频文件
  └─ ffmpeg 抽音频 (16k mono wav, 缓存复用)
       └─ Spleeter 2stem → vocals 干声   （accurate 档换 Demucs htdemucs）
            ├─ 规则层：VAD + pyin/CREPE 音高 → 持续度 + 颤音指数
            │      └─ 高置信(>0.85) → 直接判「唱」
            ├─ 模型层：vocals mel-spec → 小型 SVD-CNN (ONNX Runtime, CPU)
            │      └─ 中/低置信片段 → 帧级 singing 概率
            ├─ 灰区兜底：置信度∈[0.3,0.7] 且 时长>5s → 抽关键帧 OCR 文字密度
            │      └─ 高文字密度+无嘴型特写 → 判「BGM+文字」，压 FP
            └─ 后处理：中值滤波 → 最短2.5s过滤 → 间隙1s合并 → 输出 [start,end,conf]
输出：singing_timestamps.json + .srt
```

### 5.2 模块与依赖（压到最小）

| 模块 | 工具 | 说明 |
|---|---|---|
| 抽音频 | ffmpeg | 系统级，必装 |
| 人声分离 | Spleeter（默认）/ Demucs（accurate 档） | 抽 vocals 干声 |
| 音高/规则 | librosa（pyin）或 CREPE | 颤音、持续度硬规则 |
| 分类模型 | 小型 SVD-CNN，ONNX Runtime | 仅灰区/未决片段触发 |
| 多模态兜底 | 轻量 OCR（如 PaddleOCR 关键帧模式） | 仅真灰区触发 |
| 后处理 | 自写（滤波/合并） | 无额外依赖 |

### 5.3 档位定义（性能 vs 精度权衡）

| 档位 | 启用模块 | 典型耗时/小时视频(CPU) | 适用 |
|---|---|---|---|
| `fast` | 抽音频 + 规则层 | < 3 分钟 | 粗筛、实时性优先 |
| `accurate` | + 模型层（Demucs） | < 15 分钟 | 交付精度 |
| `verify` | + 灰区多模态兜底 | 视灰区量 | 顽固 FP 复核 |

### 5.4 验收标准（稳定好用 + 性能好 的可度量口径）

| 维度 | 指标 | 目标 |
|---|---|---|
| 准确性 | 唱歌段召回 Recall | ≥ 95% |
| 准确性 | 唱歌段精确 Precision | ≥ 92% |
| 性能 | `fast` 档单小时视频耗时 | < 3 分钟（CPU） |
| 性能 | `accurate` 档单小时视频耗时 | < 15 分钟（CPU） |
| 稳定性 | 单步失败 | 有回退（如分离失败→直接用原音频规则判），不全盘崩 |
| 稳定性 | 阈值/模型路径 | 全配置化，跨视频不必改代码 |
| 可用性 | 输出 | JSON + SRT，含置信度，可直接人工抽检 |

### 5.5 给用户的落地建议（三人共同结论）

- **先用 `fast` 档跑全量**，人工抽检误报集中在哪类（念稿？戏腔？），再针对性开 `accurate` / `verify`。
- **自有数据回流**：把人工修正后的时间戳当标签，微调那个小型 SVD-CNN，几十条样本就能显著压低你这类视频的 FN/FP——这是"稳定好用"的复利来源。
- **不要一上来就 Demucs 全模型**，长视频先 Spleeter 探路，80% 场景够用。

---

> 辩论结论：**A（稳）、B（准）、C（稳+可部署）三方一致通过「抽人声 → 规则快通道 + 小模型补漏 + 灰区多模态兜底 → 后处理出时间戳」的混合方案**，并以"召回≥95%/精确≥92%、CPU 单小时<15 分钟、失败可回退、指标可配置"作为交付验收线。


---

## 6. 第四轮：共识落地后的盲点深挖

> 第三轮已就主流程达成共识，但三人都不肯轻易收工——A、B、C 分别从「性能边界」「数据偏差」「可复现与切分」三个角度，给共识方案挑出了落地才会暴露的真问题。

### 6.1 A 批评共识里的「多模态兜底」——性能边界没锁死

**A 的批评：**
> 共识把灰区定为「置信度 ∈ [0.3,0.7] 且时长 > 5s」才触发 OCR。听起来克制，但长视频（比如 1 小时 vlog / 综艺）里「念稿 + BGM」片段可能一抓一大把，灰区总量一大，逐段抽关键帧 + 跑 OCR 的成本会失控，**直接把 `verify` 档拖垮**，违背「性能好」。

**A 的改进（给灰区再加一道闸门）：**
- 灰区**再分级**：置信度 (0.3, 0.5) 直接判「非唱」——用户首要目标是「找唱歌」，宁可漏、不可把念稿误报成唱歌污染结果；**只有 (0.5, 0.7) 且音频+画面双重存疑**才抽帧。
- 抽帧用**均匀采样 3–5 帧/段**而非密集抽帧；OCR 走轻量模型（如 PaddleOCR 的轻量版）。
- 加**灰区预算上限**：单视频 OCR 段数封顶（如 ≤ 20 段），超限转入「人工复核队列」，绝不无上限烧算力。

### 6.2 B 批评共识里的「小模型」——数据偏差与漂移

**B 的批评：**
> 小型 SVD-CNN 是用公开集（VocalSet / MIREX）训的，可用户的视频可能是**儿歌、戏腔、方言唱、二次元翻唱**——典型分布外（OOD）。模型会集体误判，而且你**根本不知道它错在哪**。共识只说「微调」却没回答三件事：**何时触发微调？怎么防小样本过拟合？怎么监控线上漂移？** 这等于把「稳定好用」寄托在运气上。

**B 的改进（主动学习闭环，把验收从「事后」搬到「在线」）：**
1. 首轮跑完输出**低置信片段清单**供人工标（和 A 的灰区清单天然复用）；
2. 累积 ≥ 30 条领域样本就 **fine-tune 最后一层**（冻结 backbone），避免小样本摧毁泛化；
3. 上线后持续监控两个量：**置信度分布熵**（突然变平/变尖 = 分布漂移）和**相邻版本 F1 差**（跌 > 2% 报警）。
> 这样「稳定好用」不再是交付时的一句话，而是**有仪表盘的持续状态**。

### 6.3 C 批评共识——可复现性 与 「唱中夹说」切分

**C 的批评（两个共识没覆盖的真问题）：**
1. **可复现 / 运维**：ffmpeg、Spleeter、ONNX 模型版本一旦变动，结果可能漂移，换台机器就崩——这直接违背「稳定」。共识只说了「缓存复用」，没说**缓存按什么键**、**版本怎么锁**。
2. **唱中夹说**：真实唱歌常是「唱一句 → 说话/换气 → 再唱」，共识后处理用「间隙 1s 合并」会把「唱-说-唱」并成一个唱歌段，**污染时间戳**；反过来又可能把长唱段里的短换气切两半。

**C 的改进：**
- **可复现三件套**：容器化（Docker）+ 依赖版本锁（锁定 ffmpeg/Spleeter/模型 hash）+ **输入哈希缓存**（同文件同参数命中缓存直接出结果，保证「同输入同输出」）。
- **间隙合并分两类**：换气型停顿（< 0.8s、两端音高连续、无新语义）合并；转说话型停顿（> 0.8s 或音高断层 + 清晰语音韵律）切断。用「音高断层 + 音节节奏突变」区分二者。

## 7. 第五轮：边界场景与最终收口

> 三人不再互相否定，而是把第四轮挑出的盲点逐个落地成可操作规则，并由 C 收口为「场景分级策略 + 最终工程验收清单」。

### 7.1 A 接 C 的「唱中夹说」——给出可操作判定

**A 的落地（零模型、透明、好调）：**
> 用**音高连续性 + 停顿时长双阈值**：
> - 停顿 < 0.8s **且** 前后帧基频差 < 1 个半音 → 视为「换气」，合并；
> - 否则视为「转说话」，切断。
> - 补充一条：停顿内若 VAD 检出「说话韵律」（短促音节、无旋律线）也切断。
>
> 全是规则，不需要再上模型，调试时一眼能看明白哪段被切、为什么被切。

### 7.2 B 接——多声部 / 分布外唱法

**B 的补充：**
1. **合唱、重唱、真假声切换**时单音高跟踪失效（多基频并存），应改用**谐波丰富度**（HPSS 谐波-冲击分离后，谐波能量占比）+ **共振峰稳定度**作为辅助唱征，**不赌单一音高**。
2. 领域自适应坚持用**最后一层 fine-tune / 线性探测**，避免小样本过拟合整网。
3. 加**分布外预警**：当某段 vocals 的「音高可跟踪率」异常低但能量高 → 标记「疑似多声部 / 特殊唱法」，进 `verify` 档人工确认，**绝不硬判**，把不确定显式暴露而不是 silently 错。

### 7.3 C 收口——场景分级策略 + 最终工程验收清单

**C 把两人补充拧成一张「场景分级表」，让方案对不同视频自动选策略：**

| 场景 | 触发判断 | 采用策略 |
|---|---|---|
| 独唱 + 清晰伴奏 | 规则高置信 | `fast` 档规则快通道直出 |
| 说话 / 念稿 + BGM | 音频灰区 + 画面文字密 | 模型层 + 灰区 OCR 兜底 |
| 唱中夹说 | 间隙内音高断层 / 说话韵律 | 音高连续性 + 停顿双阈值切分 |
| 合唱 / 戏腔 / 方言（分布外） | 音高可跟踪率低但能量高 | 谐波丰富度辅助 + `verify` 档人工/微调 |
| 极端噪声 / 分离失败 | Spleeter 报错或干声能量异常 | 回退原音频规则判 + 告警 |

**C 给出最终工程验收清单（在第三轮指标基础上补齐「可交付」的硬条件）：**

| 类别 | 验收项 | 标准 |
|---|---|---|
| 可复现 | 同输入同参数 → 结果一致 | 字节级一致（哈希缓存命中） |
| 部署 | 容器化 | 一条命令起服务，依赖锁版本 |
| 在线 | 监控 | 置信度熵 + F1 漂移报警，跌 >2% 告警 |
| 回归 | 固定回归集 | ≥ 10 段混合样本，每次改动跑回归，F1 不回退 |
| CI | 合并前必过 | 脚本 + 单测 + 回归全绿 |

> 三人确认：到此方案已覆盖主流程、性能边界、数据漂移、可复现、唱中夹说、多声部/分布外等全部分支，**可以开工**。

## 8. 最终结论（五轮后定稿）

**A（稳）、B（准）、C（稳+可部署）三方经五轮辩论，对方案达成完整一致。**

定稿方案：**「抽人声 → 规则快通道 + 小模型补漏 + 灰区多模态兜底 + 场景分级策略 → 后处理出时间戳」** 的混合架构。

核心要点（五轮沉淀）：
1. **先抽人声再判唱**（混合信号直接判必崩）——Spleeter 默认，Demucs 作 accurate 档。
2. **规则快通道 + 小模型补漏互补**：规则做高置信直判省算力，模型补规则漏检；模型仅在灰区/未决片段触发，性能可控。
3. **多模态仅作灰区兜底**：灰区再分级 + 抽帧预算封顶，长视频也不失控。
4. **唱中夹说用双阈值切分**：音高连续性 + 停顿时长，换气合并、转说话切断。
5. **分布外显式暴露**：多声部/特殊唱法进 verify 档人工确认，不硬判。
6. **可复现 + 在线监控 + 主动学习闭环**：容器化、哈希缓存、置信度熵/F1 漂移报警、低置信片段回流微调。
7. **档位化 + 配置化 + 兜底回退**：fast / accurate / verify 三档，阈值全配置，单步失败不全盘崩。

交付验收线（稳定好用 + 性能好 的可度量口径）：
- 唱歌段 **召回 ≥ 95% / 精确 ≥ 92%**；
- `fast` 档 < 3 分钟、`accurate` 档 < 15 分钟（CPU / 小时视频）；
- 失败可回退、指标可配置、**结果可复现**、**CI 回归不回退**；
- 输出 JSON + SRT（含置信度），可直接人工抽检。

> 一句话收尾：从 A 的「三件套启发式」，到 B 的「分离+模型」，到 C 的「混合+兜底+可部署」，五轮之后三方一致认为——**不押宝单一方法、把不确定显式暴露、用可量化指标收口**，才是同时满足「稳定好用、性能好」的唱歌时间戳提取方案。
